# Code review standard

## Purpose

Review the actual diff and surrounding code after development. Code review evaluates implementation correctness and engineering risk; it does not execute product acceptance testing.

## Review scope

For projects adopting the Java DDD template, read [Java DDD开发规范.md](Java%20DDD开发规范.md) and explicitly review its R/P rules: dependency boundaries, aggregate/entity behavior, assembler responsibilities, repositories, exception/logging and production adaptation. Checkstyle success does not settle these questions. Confirm the default Maven gate is enabled and the project carries its own configuration.

Inspect, as applicable:

- conformance with approved requirements and technical design;
- correctness, error handling and regression risk;
- security, authorization, privacy and secrets handling;
- data integrity, transactions, idempotency and concurrency;
- API, schema, configuration and backward compatibility;
- performance risks visible from the implementation;
- maintainability, observability and operational behavior;
- whether developer tests adequately cover changed logic and known risks.

Review the diff plus enough surrounding code to understand behavior. Do not reduce review to formatting or repeat compile, lint and unit commands already evidenced by development unless a finding or fix requires rerunning them.

## Findings

Record only actionable findings:

- P0: release-blocking data loss, security or widespread outage risk;
- P1: likely serious functional or operational defect;
- P2: meaningful defect or maintainability risk worth fixing now;
- P3: optional improvement.

Each finding needs a stable `CR-###` ID, severity, file and line when available, concrete impact, proposed correction, owner and status. If no findings exist, say so and list residual risks or areas not reviewed.

After fixes, re-review the affected code and rerun only the checks invalidated by those fixes. Return to `development` if the fix materially changes implementation or design.

## Code-review gate

The phase can become `complete` only when:

- the review scope and reviewed revision are recorded;
- all P0/P1 findings are closed or explicitly accepted by the authorized user;
- remaining P2/P3 findings and residual risks are visible;
- the result states whether the build is ready to enter independent testing.
