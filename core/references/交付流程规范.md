# 交付流程与状态模型

## 流程规模

| 模式 | 典型工作 | 启用路径 |
|---|---|---|
| Lite | 缺陷修复、脚本、小型内部改动 | 材料接收 → 需求 → 技术 → 计划 → 开发 → 代码审查 → 独立测试 |
| Standard | 已有产品的常规功能 | 材料接收 → 需求 → 产品 → 可选界面设计 → 技术 → 计划 → 开发 → 代码审查 → 独立测试 → 发布 |
| Full | 新产品、跨系统或高风险改动 | 包含 Standard 全流程，并明确界面、安全、迁移、上线与复盘关口 |

根据范围、受影响系统、用户影响、数据敏感性、可逆性和界面变化推荐模式，允许用户调整。发现实际风险显著更高时升级流程规模，并说明原因。

## 阶段状态

保留机器状态值：`not_started`（未开始）、`in_progress`（进行中）、`review`（待评审）、`approved`（已批准）、`skipped`（已跳过）、`stale`（待重新验证）、`blocked`（受阻）、`complete`（已完成）。

文档初始为 `draft`，校验后进入 `review`；只有用户在语义关口确认后才能成为 `approved`。开发、代码审查和独立测试可依据记录的证据成为 `complete`，但不能隐含替代彼此的批准或验证。

## 跨平台接续

目标项目的 `.ai-delivery/` 是流程事实源。聊天历史、模型记忆、宿主计划模式及平台任务状态只作为辅助上下文。

修改文档前：

1. 阅读 `.ai-delivery/state.json`、`AI/output/18 交接记录.md`、适用项目指令及待修改文档；
2. 记住当前数值型 `revision`；
3. 确认目标阶段未因上游变化失效，也未被上游决策阻塞；
4. 在授权范围内修改并校验；
5. 使用预期修订号调用 `record_handoff.py`。

交接会递增修订号。不匹配说明存在并发或期间变更，写入前须协调。即使模型相同，也避免多个执行主体同时修改。

平台专属配置不定义交付事实。机器状态存 `.ai-delivery/`，材料存 `AI/input/`，人类可读决策、审批、假设和验证证据存 `AI/output/`，供其他受支持宿主接续。

## 确认关口

| 关口 | 需要确认的决定 |
|---|---|
| 需求范围 | 目标、非目标、需求和验收标准正确 |
| 产品 | 用户流程、业务规则、状态和发布范围正确 |
| 技术 | 架构、契约、数据、风险和上线方案可接受 |
| 开发就绪 | 实现和开发自测已具备进入代码审查的条件 |
| 测试验收 | 独立测试支持验收，或明确识别发布阻塞缺陷 |
| 发布 | 现有证据与剩余风险支持发布 |

## 文档约定

每份实质性文档须包含：

- 元数据：项目、模式、状态、版本、更新时间和来源；
- 对应 assets 模板要求的章节；
- 可追踪事项的稳定编号；
- 明确的假设、开放问题和排除项；
- 评审后修订时的简短变更历史。

## 变更传播

默认依赖关系如下；标识符用于对应机器阶段：

```text
requirements → product → UI → technical → plan → development → code_review → testing → release
```

跳过可选阶段时，前后依赖直接衔接。开发包括编码和开发自测；代码审查评估差异与工程风险；独立测试根据需求验证产品行为，不重复代码审查。需求变更后，所有依赖它的已批准文档标为 `stale`，除非影响分析证明某份文档不受影响；记录该判断，不静默保留批准状态。

## 输入接收

接受文字、截图、图示、办公文档、PDF、本地路径、链接和连接文档。每个来源记录：

- 来源编号和描述；
- 原始路径或链接；
- 访问日期；
- 权威性：authoritative（权威）、supporting（辅助）、illustrative（示意）或 unknown（未知）；
- 相关需求编号；
- 冲突或局限。

仓库代码和可执行测试是当前行为的证据，不自动代表期望行为。
