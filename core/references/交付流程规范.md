# Workflow and state model

## Operating modes

| Mode | Typical work | Enabled path |
|---|---|---|
| Lite | bug, script, small internal change | intake → requirements → technical → plan → development → code review → testing |
| Standard | normal feature in an existing product | intake → requirements → product → optional UI → technical → plan → development → code review → testing → release |
| Full | new product, cross-system or high-risk change | all Standard phases plus explicit UI, security, migration, rollout and retrospective gates |

Recommend a mode from scope, affected systems, user impact, data sensitivity, reversibility, and UI novelty. Let the user override it. Escalate the mode when evidence shows materially greater risk; explain why.

## Phase states

Use: `not_started`, `in_progress`, `review`, `approved`, `skipped`, `stale`, `blocked`, `complete`.

An artifact begins as `draft`, becomes `review` after validation, and becomes `approved` only through user confirmation at a semantic gate. Development, code review, and testing phases can become `complete` from recorded evidence; they do not approve one another implicitly.

## Cross-platform continuity

The target project's `.ai-delivery/` is the workflow source of truth. Chat history, model memory, a platform's plan mode, and platform-specific task state are supporting context only.

Before changing artifacts:

1. read `.ai-delivery/state.json`, `AI/output/18 交接记录.md`, applicable project instructions, and the artifact being changed;
2. remember the current numeric `revision`;
3. verify that the requested phase is not stale or blocked by an upstream decision;
4. make scoped changes and run validation;
5. use `record_handoff.py` with the expected revision.

The handoff command increments the revision. A mismatch signals concurrent or intervening work and must be reconciled before writing further state. Avoid simultaneous edits from multiple agents even when they use the same model.

Platform-specific configuration files do not define delivery truth. Keep machine state under `.ai-delivery/`, input materials under `AI/input/`, and human-readable decisions, approvals, assumptions and verification evidence under `AI/output/` so another supported runtime can continue.

## Gates

| Gate | Decision |
|---|---|
| Scope | goals, non-goals, requirements and acceptance criteria are correct |
| Product | user flow, business rules, states and release scope are correct |
| Technical | architecture, contracts, data, risks and rollout are acceptable |
| Development ready | implementation and developer self-tests are complete enough to enter code review |
| Test acceptance | independent testing supports acceptance or identifies release-blocking defects |
| Release | evidence and remaining risks support release |

## Artifact contract

Each substantive artifact must contain:

- metadata: project, mode, status, version, updated date and sources;
- the required sections in its asset template;
- stable IDs for items that need traceability;
- explicit assumptions, open questions and exclusions;
- a short change history when revised after review.

## Change propagation

Use these default dependencies:

```text
requirements → product → UI → technical → plan → development → code_review → testing → release
```

Skipped optional phases collapse the edge. Development includes coding and developer self-testing. Code review evaluates the diff and implementation risks. Testing independently validates product behavior against requirements; it does not repeat code review. A changed requirement makes every dependent approved artifact `stale` unless an impact review proves that an artifact is unaffected. Record that decision instead of silently retaining approval.

## Input intake

Accept plain text, screenshots, diagrams, office documents, PDFs, local paths, URLs and connected documents. For every source record:

- source ID and description;
- original path or URL;
- access date;
- authority: authoritative, supporting, illustrative or unknown;
- relevant requirement IDs;
- conflicts or limitations.

Treat repository code and executable tests as evidence of current behavior, not automatically as desired behavior.
