# Development and developer self-test standard

## Before editing

- Confirm the technical design is approved or the user explicitly asked to implement.
- Check repository status and preserve unrelated user changes.
- Read repository instructions, the implementation plan, and the exact files being modified.
- Reconcile the plan with current code; update the plan when repository evidence invalidates an assumption.

## Coding behavior

- Implement the smallest coherent change that satisfies approved requirements.
- Follow established architecture, naming, formatting and dependency patterns.
- For Java DDD projects adopting this template, use the bundled `assets/java-ddd/reference-project/` snapshot as implementation examples. Read its README and the actual chain selected in the approved plan; inspect relevant Controller/assemblers, Application, DomainService/models, repository or OutAdaptor/converter and error handling before implementing. Generate real business names, models and logic rather than copying all demo chains. Treat the rulebook and confirmed project decisions as authoritative if examples conflict; do not rely on a machine-specific workspace/ddd path or update the shared snapshot from a business project.
- When using the approved `ddd` Java DDD template, read [Java DDD开发规范.md](Java%20DDD开发规范.md) as the current rulebook before coding; history is evidence, not competing instructions. After creating the Maven aggregation root and before production-source coding, automatically run `scripts/install_java_ddd_checks.py --project <project-root>` to install the root checkstyle.xml, inherited validate/check execution and numbered local rulebook snapshot. This is a normal template setup step, not another user confirmation gate. Preserve conflicting existing configuration and explicitly reconcile it; do not impose these rules on unrelated stacks. Without execution capabilities, generate equivalent files from assets/java-ddd and disclose that checks did not run.
- When the approved design uses Maven/Gradle modules, put source and tests in their owning module, declare only the allowed compile dependencies, and run the reactor build from the aggregation root. For newly created modules, preserve the approved `<project-name>-<layer>` naming in both directory and artifactId. Do not collapse modules into packages for implementation convenience.
- Avoid speculative abstractions and unrelated cleanup.
- For this Java DDD template, make the start POM an explicit assembly manifest of the internal modules actually deployed with this service, rather than relying only on transitive dependencies. The complete reference includes the other seven modules; trim unused, tooling-only and other-service modules for real projects. Keep test-only dependencies in test scope and dependency versions in the root POM. Review the effective dependency tree and verify the reactor build and startup path; Checkstyle does not validate this POM rule.
- Keep secrets, credentials and personal data out of code, logs and generated artifacts.
- For same-version Maven 3 modules using this template, centralize the project version in root properties/revision. Use ${revision} in the root version and each child parent version, retaining ${project.version} for root-managed internal dependency versions. Inherit the root Flatten plugin (resolveCiFriendliesOnly, updatePomFile=true; process-resources/clean executions), ignore generated .flattened-pom.xml and keep it out of snapshots. Verify default and CLI-overridden builds and an installed artifact consumed outside the source reactor; never claim a remote deploy ran unless authorized and executed.
- Define errors, validation, authorization and observability at system boundaries.
- Make schema and contract changes compatible or document migration and rollback.
- Add meaningful automated tests for business rules, boundaries and regressions in proportion to risk.
- Adapt the selected snapshot's tests to actual acceptance conditions. Replace H2, fake external responses, demonstration schema and pinned platform versions as the approved production design requires; record remaining demo-only settings explicitly, never claim the snapshot itself satisfies production requirements.
- Update user-facing or operational documentation when behavior changes.

Update `05 开发计划.md` task statuses and `14 交付追踪矩阵.md` as work completes. If development reveals a requirement or design defect, stop the affected path, record the evidence, revise the upstream artifact and mark dependents stale.

## Developer self-test

Before declaring the change ready for code review, run the applicable checks available in the repository:

1. compile, build or type checking;
2. lint and formatting checks;
3. unit tests for changed business rules and boundaries;
4. focused module, contract or integration checks owned by development;
5. a minimal smoke check of the changed path.

Record exact commands, exit status, evidence and limitations in `06 开发自测报告.md`. Unavailable, skipped and failed checks must remain distinct and must never be reported as passed. Developer self-testing demonstrates implementation readiness; it is not independent product acceptance.

## Development-ready gate

The phase can become `complete` only when:

- planned tasks are complete or explicitly deferred;
- the code and relevant documentation are updated;
- applicable developer self-tests pass, or remaining failures are recorded as blockers;
- changed files, completed task IDs, deliberate deviations and known gaps are recorded;
- the change is ready for an independent code review.

Adapt `assets/06 开发自测报告.md` for the checkpoint.
