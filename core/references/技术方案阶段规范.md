# Technical design and implementation plan standard

## Repository-first analysis

Before proposing a design, inspect relevant modules, configuration, schemas, interfaces, tests and repository instructions. Summarize the current architecture and conventions with file references. Prefer a solution consistent with the repository unless a change has a concrete benefit.

When a supplied DDD convention or repository structure defines layers such as `client`, `domain`, `application`, `infrastructure`, `adaptor`, or `start` as build modules, preserve that as a **build-time boundary**. Design a Maven/Gradle aggregator and separate submodules with explicit dependencies; distinguish business-call flow from Maven/Gradle dependency direction. For a new project, name module directories and artifactIds with `<project-name>-` prefixes, such as `<project-name>-domain`; existing repository conventions take precedence. Do not represent those module names as packages inside one application module. Only use a single module when the user or repository actually specifies one.

## Technical design

When the project adopts the `ddd` Java Maven template, read [Java DDD开发规范.md](Java%20DDD开发规范.md) and design against its current rules, not superseded historical decisions. Plan automatic installation of assets/java-ddd/checkstyle.xml and the inherited Maven validate/check gate before coding; distinguish automatic syntax checks from architecture/business rules that still need review.

Adapt `assets/04 技术方案.md` as one readable engineering loop, not a catalogue of isolated technology topics. Keep five main sections: background and value; research and core conflicts; overall solution; scope and delivery boundary; effort estimate.

Within **overall solution**, include only what materially affects the change: architecture and responsibilities, flow or sequence, model/data, **core pseudo code**, API or integration, reliability/security, observability, compatibility/rollback, and verification. The core pseudo code is required whenever code behavior changes; it must show entry, application orchestration, domain rules, state or external calls, key branches and result handling.

Mark API, migration, external calls, performance, rollout or similar content as not applicable with a reason when omitted. Diagrams should clarify a relationship or sequence; use Mermaid when repository documentation supports it, otherwise use concise text or tables. Associate externally visible contracts with stable IDs such as `API-###`, data decisions with `DATA-###`, and source facts with `SRC-###`.

## Implementation plan

For projects adopting the Java DDD template, read `assets/java-ddd/reference-project/README.md` and inspect the relevant example files when resolving implementation details. Map each coding task to the applicable write/internal-read/rule-calculation/pure-calculation/external-read chain and specific example paths. State what can be reused, what must be replaced and how it will be verified; do not require every demo mode or treat example infrastructure as an approved production design. Planning selects the examples; code generation still occurs in the authorized development phase.

Adapt `assets/05 开发计划.md`. Create small verifiable tasks `TASK-###`, ordered by dependency. Each task states:

- requirement and design IDs covered;
- files or modules likely affected;
- relevant bundled reference files and production adaptations, when this template applies;
- expected result;
- developer self-test method;
- dependency or migration order;
- rollback or containment notes when needed.

## Technical gate quality bar

- Every requirement has a technical disposition.
- External and cross-module contracts are explicit.
- Where a multi-module structure applies, the module graph and module-local package layout are both explicit, and `start` does not become a dependency of business modules.
- For the Java DDD template, identify the internal modules deployed with this service and list them directly in the start assembly POM. Do not copy every repository module by default; distinguish runtime, test-only and non-service modules. Keep versions centrally managed and plan effective-dependency/build/startup verification, not a claimed Checkstyle dependency-graph check.
- Security, migration and failure behavior match actual risk.
- For same-version Maven 3 projects adopting this template, plan root revision version management and inherited Flatten publication configuration. Verify both default and -Drevision builds, installation into a temporary local repository and independent artifact consumption; parent.version must not use ${project.version}. Existing repositories with different release/version strategies require explicit reconciliation rather than silent conversion.
- The plan separates developer self-tests from independent acceptance testing and maps both to risks and requirements.
- The plan can be executed without resolving hidden architectural decisions during coding.
