# 技术方案与开发计划阶段规范

## 优先分析仓库

提出方案前，检查相关模块、配置、数据结构、接口、测试及项目指令；引用文件说明现有架构和约定。优先与仓库保持一致，偏离时给出明确收益。

提供的 DDD 规范或仓库结构将 `client`、`domain`、`application`、`infrastructure`、`adaptor`、`start` 等层定义为构建模块时，必须保留编译期边界：设计 Maven/Gradle 聚合工程、独立子模块和显式依赖，区分业务调用流程与构建依赖方向。新项目目录和 artifactId 使用 `<project-name>-` 前缀，例如 `<project-name>-domain`；已有仓库约定优先。不能将模块名改成单一应用模块下的 package；只有用户或仓库明确采用单模块时才使用单模块。

## 技术方案

采用 `ddd` Java Maven 模板时，阅读 [Java DDD开发规范](Java%20DDD开发规范.md)，依据当前规则设计，不采用已被覆盖的历史选择。在编码前安排自动安装 assets/java-ddd/checkstyle.xml 和继承的 Maven validate/check 门禁；区分自动语法检查与仍需评审的架构、业务规则。

采用 `assets/04 技术方案.md`，形成可读的工程闭环，而不是零散技术清单。保留五个主体章节：背景与价值、调研与核心矛盾、整体方案、事项与交付边界、工时评估。

整体方案只展开实质影响本次改动的内容：架构与职责、流程或时序、模型与数据、核心伪代码、接口或集成、可靠性与安全、可观测性、兼容与回滚、验证。代码行为发生变化时，核心伪代码必须包含入口、应用编排、领域规则、状态或外部调用、关键分支和结果处理。

接口、迁移、外部调用、性能、上线等内容不适用时注明原因。图示须澄清关系或过程；仓库支持时使用 Mermaid，否则使用简洁文字或表格。对外契约关联 `API-###`，数据设计关联 `DATA-###`，来源事实关联 `SRC-###`。

## 开发计划

采用 Java DDD 模板时，阅读 `assets/java-ddd/reference-project/README.md`，解决实现细节时检查相关示例文件。将编码任务映射到写入、域内读、规则计算、纯计算或外部读链路及具体示例路径；说明复用内容、必须替换的内容和验证方法。真实项目不必包含所有演示模式，示例基础设施也不自动成为获批生产方案。计划阶段选择示例，代码只在已授权开发阶段生成。

采用 `assets/05 开发计划.md`，按依赖顺序拆成可验证的小任务 `TASK-###`。每项说明：

- 覆盖的需求和设计编号；
- 可能受影响的文件或模块；
- 采用本模板时，相关随包示例文件与生产适配；
- 预期结果；
- 开发自测方法；
- 依赖或迁移顺序；
- 必要的回滚或风险隔离说明。

## 技术确认质量要求

- 每项需求都有技术处理结论；
- 外部及跨模块契约明确；
- 多模块项目明确模块依赖图和各模块包结构，业务模块不得依赖 `start`；
- Java DDD 模板明确本服务运行的内部模块，将它们直接列入 start 装配 POM；不默认复制全仓库模块，区分运行、测试专用和非服务模块。版本集中管理，并安排有效依赖、构建和启动验证，不声称 Checkstyle 验证依赖图；
- 安全、迁移和失败行为与实际风险匹配；
- 采用本模板的 Maven 3 同版本工程，计划根 revision 管理和继承的 Flatten 发布配置。验证默认版本、-Drevision 覆盖版本、临时本地仓库安装及独立消费；parent.version 不使用 ${project.version}。已有发布或版本策略不同时，明确协调，不静默转换；
- 区分开发自测与独立验收测试，分别映射到风险和需求；
- 计划能直接执行，不把隐藏架构决策留给编码阶段。
