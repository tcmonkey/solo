# 代码审查阶段规范

## 目的

开发后检查实际代码差异及周边逻辑，评估实现正确性和工程风险；代码审查不替代产品验收测试。

## 审查范围

采用 Java DDD 模板时，阅读 [Java DDD开发规范](99%20Java%20DDD开发规范.md)，明确评审其 R/P 规则：依赖边界、聚合与实体行为、assembler 职责、仓储、异常与日志及生产适配。Checkstyle 通过不能证明这些问题已经解决；确认默认 Maven 门禁启用，项目携带自身配置。

按实际改动检查：

- 是否符合已批准需求和技术方案；
- 正确性、错误处理和回归风险；
- 安全、授权、隐私及秘钥处理；
- 数据完整性、事务、幂等和并发；
- 接口、数据结构、配置及向后兼容；
- 实现中可识别的性能风险；
- 可维护性、可观测性和运维行为；
- 开发测试是否充分覆盖改动及已知风险。

检查差异及足够的周边代码以理解行为。不将审查简化为格式检查；开发已提供编译、静态检查和单元测试证据时，除非发现问题或修复使证据失效，不重复执行同一组命令。

## 审查发现

只记录可执行的发现：

- P0：阻塞发布的数据丢失、安全或大范围故障风险；
- P1：很可能出现的严重功能或运行缺陷；
- P2：值得当前修复的明确缺陷或可维护性风险；
- P3：可选改进。

每项使用 `CR-###`，注明严重级别、可定位的文件与行号、具体影响、建议修正、负责人和状态。没有发现时明确说明，并列出残余风险或未审查区域。

修复后重新检查受影响代码，只重跑因修复而失效的检查。修复实质改变实现或设计时，返回 `development` 阶段。

## 代码审查关口

只有以下条件满足，阶段才能成为 `complete`：

- 已记录审查范围和被审查版本；
- 所有 P0/P1 已关闭，或由有权限的用户明确接受；
- 剩余 P2/P3 及残余风险可见；
- 明确说明是否具备进入独立测试的条件。
