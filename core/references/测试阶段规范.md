# Independent testing standard

## Purpose and boundary

Test from a tester or user perspective after development and code review. Derive coverage from approved requirements, product rules, interfaces and risk. Do not repeat code-style, architecture or maintainability review; those belong to code review. Do not treat developer unit tests as sufficient acceptance evidence.

## Test design

Create stable `TC-###` cases in `08 测试用例.md`. Each case should identify:

- related requirement and acceptance criterion IDs;
- priority and test type;
- preconditions, environment and test data;
- executable steps;
- expected result;
- automation status when applicable.

Cover applicable happy paths, permissions, boundaries, invalid inputs, failure recovery, compatibility, data consistency, API contracts, UI states and regression impact. Tailor the scope to the project; mark inapplicable categories instead of inventing cases.

## Test execution

Execute applicable layers:

1. functional and acceptance tests;
2. API, UI or end-to-end tests for cross-component behavior;
3. permission, boundary, exception and recovery tests;
4. targeted regression tests;
5. compatibility, migration or data-validation tests when relevant;
6. performance, load, stress or stability tests only when required by an NFR, release criterion or documented risk.

Record environment, build/revision, data, result and evidence in `09 测试报告.md`. Use `11 性能测试报告.md` only when performance testing is activated. Never report an unavailable, skipped or blocked test as passed.

## Defects and retest

Record each defect as `BUG-###` in `10 缺陷记录.md`, including severity, related case and requirement, reproduction, expected and actual behavior, evidence, owner and status. After a fix:

- return to development for implementation and developer self-test;
- repeat code review for the affected diff;
- retest the defect and impacted regression scope;
- keep the original result and append retest evidence rather than rewriting history.

## Test-acceptance gate

The phase can become `complete` only when:

- planned cases have pass, fail, blocked or not-run results;
- requirement and acceptance-criterion coverage is visible in `14 交付追踪矩阵.md`;
- all release-blocking defects are closed or explicitly accepted;
- omitted test types and environment limitations are documented;
- the report gives a clear release recommendation and residual risks.

Adapt `assets/08 测试用例.md`, `assets/09 测试报告.md`, and `assets/10 缺陷记录.md`. Adapt `assets/11 性能测试报告.md` only when performance testing is in scope.
