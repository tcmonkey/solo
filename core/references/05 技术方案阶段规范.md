# 技术方案与开发计划阶段规范

## 优先分析仓库

提出方案前，检查相关模块、配置、数据结构、接口、测试及项目指令；引用文件说明现有架构和约定。优先与仓库保持一致，偏离时给出明确收益。

提供的 DDD 规范或仓库结构将 `client`、`domain`、`application`、`infrastructure`、`adaptor`、`start` 等层定义为构建模块时，必须保留编译期边界：设计 Maven/Gradle 聚合工程、独立子模块和显式依赖，区分业务调用流程与构建依赖方向。新项目目录和 artifactId 使用 `<project-name>-` 前缀，例如 `<project-name>-domain`；已有仓库约定优先。不能将模块名改成单一应用模块下的 package；只有用户或仓库明确采用单模块时才使用单模块。

## 技术方案

采用 `ddd` Java Maven 模板时，阅读 [Java DDD开发规范](99%20Java%20DDD开发规范.md)，依据当前规则设计，不采用已被覆盖的历史选择。在编码前安排自动安装 assets/java-ddd/checkstyle.xml 和继承的 Maven validate/check 门禁；区分自动语法检查与仍需评审的架构、业务规则。

采用 `assets/04 技术方案.md`，形成可读的工程闭环，而不是零散技术清单。保留五个主体章节：背景与价值、调研与核心矛盾、整体方案、事项与交付边界、方案反思与可行性推演。

整体方案只展开实质影响本次改动的内容：架构与职责、流程或时序、模型与数据、核心伪代码、接口或集成、可靠性与安全、可观测性、兼容与回滚、验证。代码行为发生变化时，核心伪代码必须包含入口、应用编排、领域规则、状态或外部调用、关键分支和结果处理。

接口、迁移、外部调用、性能、上线等内容不适用时注明原因。图示须澄清关系或过程；仓库支持时使用 Mermaid，否则使用简洁文字或表格。对外契约关联 `API-###`，数据设计关联 `DATA-###`，来源事实关联 `SRC-###`。

## 方案生成后的反思与可行性推演（必做）

完整方案草案生成后、交付确认前，对整份技术方案主动做一次风险相称的反思推演；重大修改后重推演受影响链路。这是技术阶段的质量要求，不增加独立用户审批，也不替代后续开发自测、CR或独立测试。所有模式均执行，小改动可用简短段落；需求与产品重点是范围和行为表述清楚，不照搬重技术评审。

从关键需求出发贯穿入口、模块、状态、存储、外部调用和结果，检查架构/构建边界、版本与依赖兼容、数据模型、接口、事务/并发/幂等、安全与隔离、故障恢复、资源上限、迁移/回滚及验证路径。按实际风险选择正常链路和反例：重复、交错提交、断流、部分成功、重启、删除/撤销、过期、超限等；不适用项说明原因，不机械增加无关专项。

反思记录至少说明具体场景/假设、推演结果、发现的问题、修订位置、修订后的重新推演、证据类型和剩余验证条件。发现矛盾须回改正文、伪代码、数据/接口契约和关联任务，不能只在第五章列问题而保留相反实现指令。阻断问题未闭环时不能声称方案可直接执行。

区分“逻辑推演”“已执行实验”和“待验证”；选择必要且已授权的最小实验检验高风险假设，缺环境/权限时记录条件和验证任务。不把DDL通过、依赖元数据可获取、模板齐全或清单打勾当作整体可行性证明，不虚构执行证据。结论明确当前可行范围、前置条件及未证明的生产能力。

## 开发计划

采用 Java DDD 模板时，阅读 `assets/java-ddd/reference-project/README.md`，解决实现细节时检查相关示例文件。将编码任务映射到写入、域内读、规则计算、纯计算或外部读链路及具体示例路径；说明复用内容、必须替换的内容和验证方法。真实项目不必包含所有演示模式，示例基础设施也不自动成为获批生产方案。计划阶段选择示例，代码只在已授权开发阶段生成。

默认在 `04 技术方案.md` 的整体方案下嵌入开发计划，按依赖顺序拆成可验证的小任务 `TASK-###`。只有任务规模、多人协作或独立排期确需拆分时，采用 `assets/专项文档/开发计划.md`，主文档链接而不重复维护。每项说明：

- 覆盖的需求和设计编号；
- 可能受影响的文件或模块；
- 采用本模板时，相关随包示例文件与生产适配；
- 预期结果；
- 开发自测方法；
- 依赖或迁移顺序；
- 必要的回滚或风险隔离说明。

默认不生成人天、工时、合计工期或替负责人决定排期。计划提供任务依赖、实现结果、验证和风险，实际排期由当事人依据当前情况决定；只有用户明确要求估算时才按已知依据列假设、不确定性和范围，不将估算写成承诺。

## 技术确认质量要求

- 每项需求都有技术处理结论；
- 外部及跨模块契约明确；
- 多模块项目明确模块依赖图和各模块包结构，业务模块不得依赖 `start`；
- Java DDD 模板明确本服务运行的内部模块，将它们直接列入 start 装配 POM；不默认复制全仓库模块，区分运行、测试专用和非服务模块。版本集中管理，并安排有效依赖、构建和启动验证，不声称 Checkstyle 验证依赖图；
- 安全、迁移和失败行为与实际风险匹配；
- 采用本模板的 Maven 3 同版本工程，计划根 revision 管理和继承的 Flatten 发布配置。验证默认版本、-Drevision 覆盖版本、临时本地仓库安装及独立消费；parent.version 不使用 ${project.version}。已有发布或版本策略不同时，明确协调，不静默转换；
- 区分开发自测与独立验收测试，分别映射到风险和需求；
- 计划能直接执行，不把隐藏架构决策留给编码阶段；
- 已完成整份方案生成后的反例推演，发现的问题已同步修订并重新推演，未验证假设和阻断项明确。


## 工程边界与异常入口约束

有前端时，默认自动建立服务端同级`<项目名>-app`独立应用，不嵌入服务端frontend目录；已有布局及用户明确指定优先，保留同名既有目录。前后端分别锁依赖、构建，启动/代理/文档引用同步。

AI生成设计、接口/数据库说明、草稿和检查证据归AI/output，输入归AI/input；不默认增加代码根docs/database目录。正式迁移、运行配置、业务源码、测试、构建启动脚本和根README保留实际构建位置，不维护双份DDL。

Controller/输入端口、Application、DomainService、OutAdaptor实现各自主调用入口必须本方法try-catch覆盖组装/调用/转换，捕获业务及未知Exception后返回安全失败；禁止向外抛出、声明throws或catch重抛，不用全局处理器替代。内部不变量/协作可抛异常由本层入口捕获；异步/流式按协议安全失败终止。应用catch须包住事务执行/提交，失败Result明确回滚，不能吞异常提交部分写入。Java细则与门禁范围按99规范ERR-004/006/007、MOD-010、DEL-006。
