# 交付流程与状态模型

## 1. 完整路径与裁剪

01 需求梳理 → 02 产品方案 → 03 UI设计（按需）→ 04 技术方案与计划 → 05 编码开发 → 06 开发自测 → 07 代码评审（CR）→ 08 独立测试 → 09 发布准备 → 10 初始发布 → 11 发布观测 → 12 分批放量 → 13 完整发布确认 → 14 效果评估。

流程编号用于用户理解，不改变机器阶段和文档命名。01 对应 intake + requirements，04 对应 technical + planning；其余逐步对应 product、ui、development、developer_self_test、code_review、testing、release_preparation、initial_release、observation、rollout、full_release、effect_evaluation。材料接收是需求前置动作，文档数量不等于阶段数量。

| 模式（内部标识） | 用途与默认路径 | 默认裁剪 |
|---|---|---|
| 简易（lite） | 小需求、修复、脚本；01 → 04 → 05 → 06 → 07 → 08 | 02 的必要规则并入需求，04 简短，08 保留必要功能验收；实际上线时启用09～14 |
| 平衡（standard） | 常规功能；01 → 02 → 04 → 05 → 06 → 07 → 08 | 独立方案和测试；UI按需，09～14根据交付目标进入 |
| 完整（full） | 新项目、跨系统或高风险；01 → 02 → 04 → 05 → 06 → 07 → 08 → 09～14 | 强化安全、性能、兼容、迁移和回滚；UI仍按需，本次也可先停在方案 |

实际需要发布的 Lite 项目也必须启用发布子阶段，不能用模式名规避质量关口。允许有理由裁剪 UI、性能专项、放量方式等；记录原因、风险和批准人。小型一次性发布没有分批条件时，明确记录 rollout 不适用，仍须初始发布、观测与完整确认。标准流程不预设用户已授权生产操作。

### 1.1 首次启动：先介绍，再收必要信息

裸调用先展示完整14步及上表，只问未知的项目和需求/附件，不把模式、步骤编号或终点作为必填项。示例回复：`项目：itineary；需求：增加行程复制功能。` 不扫描整个多项目工作区寻找潜在需求，未确定目标前不初始化、不检查全部模块和工具。

有背景后推荐模式并解释：小范围低风险改动用简易，常规功能用平衡，高风险/跨系统/支付/安全/数据迁移用完整。没有背景时平衡仅为暂定建议，不假装已评估风险。已有附件足够理解时不要求用户重复写背景。

### 1.2 模式与本次终点分别记录

| 成果终点 | execution_goal | 暂停步骤 |
|---|---|---|
| 方案想清楚 | plan_only | 04 技术方案与计划，包含必要设计和伪代码，不编码 |
| 功能可运行（自测和CR完成） | development_ready | 07，不代表独立测试或上线完成 |
| 上线前可验收（含发布准备） | release_ready | 09，不部署生产 |
| 上线交付闭环 | full_delivery | 14；生产执行仍须授权与真实数据 |
| 暂未选择 | auto | 新需求推荐07并在范围确认时一并确认；既有项目沿用原计划，不强行缩短 |

终点可选且可从自然语言识别，也允许阶段级自定义暂停点（工作台记录原始诉求和机器阶段，不伪装成某个成果终点）。整体需要但本次终点之后的阶段保留 not_started/原状态，在路线展示为“本次暂不执行”，不能标完成或仅因暂停标skipped。真正不适用与合并步骤须说明理由。改变终点保留审批、阶段证据与revision历史，不构成生产授权。

需求理解后展示推荐模式及理由、终点、本次编号路线，以及02合并、03按需、后续暂不执行等原因；随后确认需求范围，不增加一个独立的强制模式选择关口。每次进入阶段说明工作、所需材料和产物，只询问当前缺失项。已有项目先展示真实进度、当前步骤、下一步与缺失材料；到达终点时暂停提供继续选项，不重复启动问卷。

## 2. 文档映射：9 份主文档，按需生成

| 文件 | 记录内容 |
|---|---|
| 00 交付工作台.md | 摘要、阶段索引、需求追踪、审批决策、假设问题风险、变更、交接 |
| 01 需求文档.md | 诉求调研、背景、期望价值、范围和验收 |
| 02 产品方案.md | 用户流程、业务规则、实现手段及可行性；小需求可并入需求 |
| 03 界面设计方案.md | 确有界面变化时生成 |
| 04 技术方案.md | 技术闭环、核心伪代码及嵌入式开发计划 |
| 05 开发交付记录.md | 编码变更、开发自测、CR 各自独立的证据与结论 |
| 06 测试验收报告.md | 用例、执行、缺陷、复测，按需性能、兼容及回滚验证 |
| 07 发布运行记录.md | 准备、初始发布、观测、放量、完整确认、回滚与数据交接 |
| 08 效果评估与复盘.md | 业务与技术目标、数据评价、归因、经验及技能优化候选 |

初始化只生成工作台、AI/input/00 输入材料清单.md 和机器文件。进入阶段且有实质内容时，基于相应 assets 模板生成文档；不提前创建空白测试、发布、复盘报告。不适用章节说明理由，不为填表编造信息。未来索引应标明“未生成”，不做不存在文件的链接。

复杂项目确需独立任务管理或性能专项时，采用 assets/专项文档/ 中的模板；在工作台记录拆分理由和唯一可编辑位置，主文档仅保留摘要和链接。不重复维护同一任务或结果。Java DDD 项目的 19 Java DDD开发规范.md 是随工程的编码约束副本，不是业务阶段模板。

所有阶段产物位于 AI/output，以 Markdown 和两位序号中文名保存；原始素材位于 AI/input；JSON/YAML 配置、状态及只读迁移归档位于 .ai-delivery。SKILL.md、README.md 等协议入口保留标准名称。

## 3. 状态、审批与事实源

state.json schema 1.5 / template 0.8.0 / artifact_layout consolidated-lazy 是流程事实源。机器阶段见 scripts/delivery_model.py；不得把共享文件的一个 frontmatter 状态当作全部阶段的状态。工作台同步展示逐阶段结论。

本次引导为向后兼容更新：新初始化可写execution_goal，旧0.8.0缺少该字段仍可读取/校验，不触发文档迁移。delivery_mode独立控制详略；终点不是状态、不是审批。state与profile的已选终点须一致，确认后在工作台摘要记录路线并按revision同步交接。只读preview_delivery.py只输出介绍/建议和现有进度，不写状态，也不替用户评估未知需求或批准生产。

状态：not_started、in_progress、review、approved、skipped、stale、blocked、complete。需求、产品、技术由用户确认后 approved；编码、自测、CR、测试依据实际证据完成。未执行不能算通过；结构校验通过不等于语义验收。

guided 在需求、产品、技术、开发就绪、测试验收及发布关口确认；continuous 只覆盖明确授权的范围。初始发布和各批放量必须有授权、版本、环境、比例、观察窗口和回退条件；超出已授权范围时重新确认。

## 4. 追踪、变更与跨宿主交接

来源 SRC、需求 REQ、设计 TECH、任务 TASK、接口 API、审查 CR、测试 TC、缺陷 BUG 和决定 DEC 使用稳定 ID。工作台维护追踪关系、审批范围和关键证据；事实、假设、冲突和未知必须区分。

操作前读取 state.json、工作台第 7 节及项目指令，记下 revision；修改上游时明确影响分析，将已完成且受影响的下游阶段标为 stale。跳过可选阶段时记录原因，不静默绕过关键关口。

一个项目只允许顺序交接，不同宿主不同时编辑。record_handoff.py 用修订号、锁和事务同步工作台与状态；revision 不匹配先重新读取协调，禁止覆盖新状态。artifact_overrides 可将 product 映射到 AI/output/01 需求文档.md，或将 planning 映射到专项文档；路径必须保持在 AI/output 内，主文档和工作台说明原因。

迁移由 migrate_project.py 执行，先归档原文及校验和再合并；保留审批和历史交接，不能从旧自测推断 CR 完成，也不能从旧发布检查推断已经发布、放量或效果达标。

## 5. 结束检查点

说明当前阶段、产物、重要决定、风险、真实校验证据和下一步。在没有生产访问或数据的情况下，发布与效果阶段保留未执行或有理由不适用，不能编造生产观测和商业价值。
